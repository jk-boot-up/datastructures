1. Dynamic Array (Recursive)

Hello, and welcome. This video explains the dynamic array, written recursively, in C. This video is presented by Jayasekhar Konduru. First, a simple definition. A dynamic array keeps an ordinary array inside, and moves to a bigger one when it is full. Here, every loop is written as a recursion: a function that handles one element, and calls itself for the rest. Our example is a music playlist that grows one song at a time. By the end, you will know how each loop becomes a recursion, what that costs in memory, and why an ordinary append can crash.

2. The Everyday Idea

Think of a family moving house, with a line of helpers. The first helper carries box zero, then asks the next helper to carry the rest, and waits. The second carries box one, asks the next, and waits too. The last helper finds no boxes left, and says done. That is the base case. With four boxes, four helpers wait. With a million boxes, the corridor is not long enough. That is a stack overflow.

3. The Words

The words. The size is how many elements are in use, and the capacity is how many places there are. A resize makes a new array, and copies every element. The base case is when nothing is left to copy. And the recursion depth is the number of frames at once. A recursive resize of n elements needs n frames.

4. Act One — A recursive copy

First, a recursive copy. The playlist is full, with four songs. To append a fifth, it must resize to eight. Copy zero copies Blue Sky, and calls copy one. Copy one copies Rain Dance, and calls copy two. And so on, until copy four finds nothing left. That is the base case. Four copies, four frames on the stack.

Here is the call stack at the deepest point. Four copy calls, each waiting. On top, copy four, the base case. When it returns, the others return one by one.

6. Act Two — Growing

Growing. The next three songs cost one write each. The ninth song finds the array full again. The resize to sixteen copies eight songs, eight frames deep. Nine appends, two resizes, twelve copies, exactly as with loops. Recursion does not change the time. It changes the stack.

Here is the playlist now. Nine songs in sixteen places. The second resize copied eight songs, with eight calls waiting at once.

8. Act Three — The middle, recursively

Now the middle. Inserting an intro at the front shifts all nine songs, nine calls deep. Deleting index five shifts four songs, four calls deep. And searching for Firefly finds it at index seven, eight calls deep. Each time, the depth is the number of elements visited.

10. Act Four — Shrinking, recursively

Shrinking uses the same recursive copy. Shrink to fit copies nine songs into exactly nine places, nine calls deep. And when deletions leave only a quarter of the places in use, the array halves itself. From thirty two places to sixteen, copying eight songs, eight calls deep.

11. Shrinking, recursively

Here is the shrink. The old array had sixteen places. The new one has exactly nine, and every song was copied by its own call.

12. Act Five — The limit of recursion

And the limit. We try to append a million songs. Long before the end, a resize has to copy more songs than the call stack has room for. The operating system stops the program, from inside an ordinary append. So the demo ran it in a separate child process. The loop version finishes. Recursion is fine when the depth is small, and dangerous when it grows with the data.

13. The limit of recursion

Here is the problem. One copy call per element, all waiting. For a big resize, that is more frames than the call stack can hold.

14. Time and Space Complexity

Here are the costs. Get and update are order one, and not recursive. Append is order one amortised, but a resize takes order n time and order n stack. Insertion and deletion at the front take order n time and stack. So do traversal and linear search. The loop version takes the same time, with order one extra space.

15. Recursive or Loop?

Recursive or loop? The counts are the same: twelve copies for nine appends. But recursion keeps one frame per element copied, and the loop keeps none. For a large resize, the recursion overflows the call stack, and the loop simply finishes.

16. Common Mistakes

Four mistakes to watch for. A recursive copy with no base case. Forgetting that resize is recursive, so an append can overflow. Shifting from the insertion position upwards, which overwrites the data. And not clearing a deleted place, which keeps the old string alive.
